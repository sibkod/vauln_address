## Payments (SOL order verification)
- ALL payment-completion paths (POST /api/orders/:id/confirm, GET /api/orders/verify, POST /api/payment/status/:signature) verify the tx ON-CHAIN before crediting anything: services.PaymentVerifier.VerifyPaymentTx (internal/services/payment_verifier.go) fetches getTransaction(jsonParsed) and proves: meta.err == nil (failed/reverted tx → reject), the order's payment_address gained >= order token_amount (account balance diff post−pre; parsed system-transfer instruction as fallback when the recipient funds the tx; 0.5% slack for the 4-decimal rounding in CreateOrder), fee payer == order wallet, blockTime within 2h of order creation (older txs can't be replayed onto new orders). Rejections are *services.VerificationError with codes TX_FAILED / AMOUNT_MISMATCH / WRONG_SENDER / TX_TOO_OLD and mark the order failed (TX_TOO_OLD → expired) via rejectOrderPayment; RPC/transport errors are retryable (503, order stays pending).
- Replay protection: GetOrderByTxHash — a tx already tied to a completed order → 409 TX_ALREADY_USED.
- Balance credit is atomic: repository.CompleteOrder returns rowsAffected of the pending→completed UPDATE; only a true transition credits AddUserBalance (settleVerifiedPayment). Double-submit/concurrent verification → "already_completed", no double credit.
- The old message-signature body path of ConfirmOrder and the auto-complete in VerifyPayment are GONE (they credited checks without any on-chain proof). Frontend uses only /api/payment/status polling (PricingView).
- Tests: internal/services/payment_verifier_test.go (mock RPC: confirmed/failed/wrong recipient/underpaid/wrong sender/too old/not-found retryable/self-transfer), internal/handlers/payment_test.go (full handler flows + CompleteOrder atomicity). New users start with balance = FreeCheckLimit (UpsertUserNonce seeds it).


## Performance conventions (MySQL at millions of rows)
- DB pool is env-tunable: DB_MAX_OPEN_CONNS (50), DB_MAX_IDLE_CONNS (10), DB_CONN_MAX_LIFETIME_MIN (5); zero values in hand-built Configs fall back to the same defaults. MySQL DSN carries interpolateParams=true + 5s/30s timeouts.
- InsertScanFinding is a single-round-trip per-dialect upsert (INSERT IGNORE / OR IGNORE / ON CONFLICT DO NOTHING + RETURNING); duplicates resolve the existing id via a follow-up SELECT by signature.
- Wallet creation is serialized per chain+address by a striped mutex (repository.walletInsertLocks, 256 stripes): CreateWallet re-checks existence under the lock and returns the existing id on a duplicate, MarkAssociatedHacker holds the lock across its update-or-insert. This substitutes the missing UNIQUE(chain,address) within one process (tests: TestCreateWallet_ConcurrentNoDuplicates, TestMarkAssociatedHacker_ConcurrentNoDuplicates).
- /api/monitor/stats is served from a 30s in-memory cache on the Handler (mutex = single-flight; a failed refresh keeps serving the last good snapshot); the underlying GetScanStats is a full-table aggregate.
- BatchAddWallets: in-batch dedupe + bulk existence check (address IN ...) + multi-row INSERT chunks of 500, ids read back per chunk (no per-row LastInsertId).
- Report assembly loads the root address's scan findings and flow payouts ONCE (assembleReport) and passes them into buildStatusEvidence (first 20 = evidence), buildTxTree (prefetchedFindings for the root fillTxNode call) and buildFundFlows. Tree node status+association come from one query (repository.GetWalletStatusAndAssociation, handler treeNodeInfo); the tree root keeps the lenient treeNodeStatus behavior.
- Rate limiter middleware does ONE rate_limits read per request (expired windows reset inline); checkAndResetWindow no longer exists.
- Still open (needs schema work, deliberately avoided): LIKE '%…%'-scans on scan_findings.sweeps/exposed_addresses/indicators (GetScanFindingsForAddress, GetFlowPayoutsForSource) can't use indexes without normalizing those CSVs into child tables; wallets has no UNIQUE(chain,address); check_history lacks a composite (wallet_address,address,chain) index.

## Wallet statuses
- Single source of truth: `statusCatalog` in internal/models/models.go (13 statuses: hacked, vulnerable, safe, hacker, drained, phishing, scam, mixer, sanctioned, exchange, suspicious, frozen, unknown) with label, severity (danger/warning/info) and description. `IsValidStatus`/`ValidStatusNames`/`StatusDescription` derive from it; report details and the admin import error use these helpers.
- Public catalog endpoint: `GET /api/statuses` (handlers.GetStatuses). Frontend mirrors the catalog in HomeView/ReportView/ChecksView statusMeta maps and global CSS (`.dot.danger|vulnerable|success`, `.alert-status.<status>` in style.css).
- Scanner ingest: DRAINER → victim `drained` + hacker `hacker`; SUSPICIOUS → counterparty `suspicious`. Program findings (hacker = takeover program) create NO hacker-association flags: their exposed addresses are hijacked victims, not funders, and a takeover victim never funded anyone; the victim address is also always excluded from association marking; MarkAssociatedHacker skips the update when the same reason is set already (COALESCE-guarded LIKE, per-dialect). A takeover-only finding (P1 without P2/P6) names the owning on-chain PROGRAM as hacker — the assign instruction never invokes the owner program, so it may be missing from `programs`; ingest never registers it as a hacker wallet (isTakeoverOnlyFinding), and the scanner merges takeover new_owners into finding.programs (finding_programs in solana_scan.py, all 3 posting sites).
- Hacker association (migration 006): `wallets.associated_hacker` + `associated_reason` flag wallets that sent funds INCOMING to a hacker/drainer address. Scanner findings carry `exposed_addresses`; IngestScanFinding calls `repository.MarkAssociatedHacker` — unknown senders are inserted with status `unknown`, existing statuses are never overridden (association is a flag, not a danger verdict). Report response and tx-tree nodes expose the flag; frontend shows a 🕸️ badge (TxTreeNode) and a banner (ReportView).
- Tests: internal/models/models_test.go validates catalog/validation sync; internal/handlers/scanner_test.go TestIngestScanFinding_MarksAssociated covers the association flow.

## Data conventions
- DB access supports postgres/mysql/sqlite; all queries use `?` placeholders and per-dialect upserts (see UpsertUserNonce).
- `check_history.wallet_address` doubles as report-access key: authenticated wallet address, or `ip:<ip>` for anonymous users (repository.AnonymousRequesterPrefix). Anonymous rows older than 24h are deleted by ReportCleanupService, which implements report expiry (models.AnonymousReportTTL).
- `wallets.reason`/`wallets.source` (migration 004) feed the report endpoint; `leaked_keys` (migration 003) supplies leak metadata — never expose `key_value`.
- Runtime schema (repository.InitSchema) does not create `leaked_keys`; report code tolerates missing table.

## Report endpoint
- `GET /api/report?address&chain` — access only after same requester ran `/api/check`; 403 REPORT_NOT_AVAILABLE / REPORT_EXPIRED, 404 when not in DB. Transaction tree comes from indexed scan_findings (deterministic), child statuses: DB status else heuristic unknown/potential_hacker.
- Public sharing without schema changes: share token = UUID of [8-byte check_history.id][8-byte HMAC-SHA256(auth.JWTSecret, "report-share-v1|id")]. `POST /api/report/share` (RequireAuth) mints it, `GET /api/report/shared/:id` serves publicly. Only authenticated users can mint; revoking = deleting the check_history row (never happens for auth rows). See internal/handlers/report_share.go.
- Report transaction tree (buildTxTree in handlers/report.go) is built from indexed scan_findings: each node aggregates that wallet's own findings (tx_count/amount), children = counterparties grouped per address with status from DB or heuristic unknown/potential_hacker; per-node caps reportTreeDepth/reportTreeMaxNodes/reportTreeMaxChildren/reportTreeFindingsCap. Empty when no findings exist. Traversal stops at hacker wallets (sinks of the stolen funds). Program nodes are NOT sinks: the tree expands them to the real payout recipients — flow-trace findings (F1/F2) persist their funding sources in scan_findings.exposed_addresses (migration 007; repository.GetFlowPayoutsForSource matches CSV elements per-dialect), so every wallet paid by the program/operator becomes a child. Recurrence classifies unregistered recipients: 2+ findings or F2 → hacker, one-off F1 → suspicious; registered wallets keep their DB status (ingest registers F2 as hacker / F1 as suspicious). Program-node children are recipients only — victims drained through the program are not repeated under it. Tests: TestGetReport_TreeExpandsProgramPayouts, TestIngestScanFinding_TakeoverProgramNotRegistered. A counterparty listed in the finding's `programs` is an on-chain program, not the hacker wallet: node gets `is_program: true` + status `program` (models.TreeStatusProgram, frontend ⚙️ badge); IngestScanFinding likewise skips registering such an address as hacker/suspicious. TxTreeNode.vue shows full (untruncated) addresses.
- Frontend: `/report/:id` (public) and `/report?address&chain` (owner view) both render ReportView; "Make public & share" only for connected wallets, anon sees a lock notice.
- Tests: `internal/handlers/report_test.go` runs the real handler against real SQLite (TempDir), seeds via repository.CreateWallet + raw SQL for leaked_keys (migration 003 table, not in InitSchema), backdates check_history with UTC "2006-01-02 15:04:05" strings. CheckWallet records history in a goroutine — poll GetLastReportAccess in tests. Report page long lists are capped in scroll blocks in ReportView.vue: evidence chain in `.evidence-scroll` (340px), money-flow columns and the tx tree in the shared `.scroll-block` (340px; tree adds `.tree-scroll` 480px + overflow-x auto), leaks table in `.table-scroll` (overflow-x). TxTreeNode `.tx-addr` wraps full addresses with `overflow-wrap: anywhere` (never truncates).
- Go toolchain in this sandbox may be missing; install to /tmp/go and export PATH=/tmp/go/bin, GOPATH=$HOME/gopath.

## Drainer scanner (solana_scan.py) integration
- Scanner posts findings to `POST /api/admin/scanner/findings` (X-Admin-Key = ADMIN_API_KEY, or flags `--api-url/--api-key`, env `VAULN_API_URL`/`ADMIN_API_KEY`). Findings stored in `scan_findings` (unique `signature`); DRAINER findings auto-register victim as `drained` and hacker as `hacker` in wallets (source `solana_scan`), and flag every `exposed_addresses` entry (senders funding the operator) as `associated_hacker` via MarkAssociatedHacker.
- Live monitoring: public `GET /api/monitor/findings?after_id` (after_id = incremental ascending polling) and `GET /api/monitor/stats`. The feed is hard-capped at the latest monitorFeedLimit = 10 findings — `limit`/`before_id` params were removed, older history is not served; frontend page `/monitor` (MonitorView.vue) polls every 4s and keeps only the 10 newest rows. The page is multi-chain: each card shows a chain badge (components/ChainLogo.vue inline SVG logos + chains.ts meta: symbol/decimals/explorer URLs/block label), an operation type derived from verdict+indicators (P1→Account takeover, F2→Hacker moving funds, F1→Downstream transfer, DRAINER→Wallet drained, else Suspicious activity) with adaptive party labels, amount in the chain-native symbol, and per-chain explorer links. No stats and no indicator chips (P-codes).
- Scanner findings may carry specific EVM networks besides the canonical chains: models.IsScanChain = IsValidChain | IsEVMNetwork (ethereum, bnb, base, linea, arbitrum, polygon, optimism, avalanche). IngestScanFinding keeps the specific network in scan_findings for display but validates addresses and registers wallets under models.CanonicalChain (= evm for those networks); report.go chainCurrency maps them to native symbols, treeValidationChain normalizes via CanonicalChain. Test: TestIngestScanFinding_SpecificEVMNetwork.
- frontend/src/chains.ts (getChainMeta) holds display name/native symbol/decimals/explorer tx+address URLs/block label for the canonical chains and the specific EVM networks; unknown chains fall back to their raw name with solana explorer links. frontend/src/components/ChainLogo.vue renders inline SVG logos per chain (letter fallback). Used by MonitorView badges and by components/ChainSelect.vue — the custom dropdown replacing the native <select> on HomeView (style.css light-theme overrides keep it themed; .search-box needs position:relative+z-index for the menu to overlay the result box).
- User drainer reports: `POST /api/drainer-reports` requires a one-time SVG captcha from `GET /api/captcha` (services.CaptchaService, in-memory, 10min TTL; `Answer(id)` is a test hook). Stored in `drainer_reports`, forwarded to Telegram via services.TelegramService (TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID); delivery flag `telegram_sent`. Frontend page `/report-drainer` (ReportDrainerView.vue). Scanner review: on first insert, a finding WITH programs but WITHOUT the P5_KNOWN_DRAINER_PROGRAM indicator (pattern fired on a program not in the watchlist) is forwarded to Telegram for analyst review (best-effort goroutine, never blocks ingest); response exposes `needs_review`; the amount label uses chainCurrency (TRX/BTC/…, not always SOL). Live-block findings carry no programs, so they never trigger review.
- Report endpoint includes `evidence` chain (models.StatusEvidence): registry listing, key leaks, scanner indicators P1..P6 with tx/counterparty/amount. Meta for P-codes lives in handlers/scanner.go (scanIndicatorMeta) — mirror of detect_patterns in solana_scan.py.
- scan-wallet mode resolves the real operator per transaction via extract_parties (sweep destination / takeover new owner / non-victim signer); the scanned wallet is the hacker only when it actually received a sweep transfer. The API ingest also drops findings where hacker == victim (malformed scanner output). The wallet report JSON lists all operator wallets in `operator_wallets` (sweep destinations + takeover owners with swept SOL).
- solana_scan.py whitelist: `solana_programs.json` (~290 known program IDs, sources in file header) auto-loaded at startup (`--programs-file` / env `SOLANA_PROGRAMS_FILE`); embedded KNOWN_PROGRAMS is the fallback. Detectors: P1 account takeover, P2 ≥90% SOL sweep, P3 unknown program, P4 control account, P5 drainer watchlist, P6 signer token sweep (preTokenBalances→0). Verdict DRAINER = P1 | P5+(P2|P6); (P2|P6)+P3 is SUSPICIOUS. P6 requires >=2 mints swept with no SOL compensation (single-token full swaps are legit). Never whitelist addresses from KNOWN_BAD_PROGRAMS. KNOWN_BAD_PROGRAMS embeds the drainer-side companions 4PG6e97/J9kkSCM (invoked alongside the syspv6 takeover in the 22.08.2026 review cases).
- Tests: internal/handlers/scanner_test.go reuses setupReportTest (real SQLite); scanner.go holds all new handlers.
- Scanner test fixtures must use valid base58 32B Solana addresses (9ML9o4nY…, 4QFiKg8…, 27Jc8…, 56qGwV…, 9cgS3V…, HjPZYp… constants at top of scanner_test.go) — IngestScanFinding rejects anything failing validators.ValidateAddress, and report.go fillTxNode filters invalid counterparties from the tree via treeValidationChain(finding.Chain, reportChain).
- Public Solana RPC endpoints: treat `result:null` on getTransaction as an endpoint failure and rotate (solana-rpc.publicnode.com serves null for historical tx). Never batch getTransaction — public nodes return 429/null for batches; fetch one tx per call with a second pass over nulls (Rpc.get_transactions). Cache cleanup: purge null entries from drainer_cache at scan start.
- Multithreading: the scanner is built for high-rate-limit RPCs (Helius). `--rpc-url` (repeatable, env `SOLANA_RPC_URL`) replaces the default public endpoints (round-robin across all of them); `--threads` (env `SOLANA_SCAN_THREADS`, default 8) sizes the ThreadPoolExecutor used by Rpc.get_transactions, trace_fund_flows (per-level frontier), FindingPoster (API ingest) and the watch block loop; `--rpc-delay` adds per-call pacing. Rpc is thread-safe (endpoint rotation under a lock). For public RPCs use `--threads 1 --rpc-delay 0.8` (old sequential behavior). Watch mode processes blocks in a sliding window (`--window`, default 4*threads): workers claim slots from a shared cursor, findings are recorded out of order as blocks complete, and slots beyond window from the oldest unfinished one don't start (a run of skipped blocks can't race the cursor far ahead). With 3 endpoints it sustains ~3 blocks/s (chain pace ~2.5).
- Finding dedup: scan_findings.signature is UNIQUE, and FindingPoster additionally dedups by signature within a run (same tx can surface via several hijacked accounts or downstream findings), so parallel posting never races the constraint. InsertScanFinding still treats a unique-violation on INSERT (select-then-insert race) as a duplicate: re-selects and returns (existing id, false) instead of 500 (isUniqueViolation matches sqlite/mysql/postgres error strings). Tests: internal/repository/scan_test.go (TestInsertScanFinding_Dedup, TestInsertScanFinding_ConcurrentDedup with -race).
- Split drains (migration 008): `scan_findings.sweeps` is a CSV of "address:amount_sol" pairs — the per-recipient breakdown when the stolen funds are divided between several wallets in one tx (scanner `sweep_breakdown`, aggregated per destination, largest first; hacker_address stays the largest recipient). Ingest validates/filters sweeps like other addresses and registers secondary recipients as `suspicious` (registerSweepRecipients, response field `sweeps_added`). GetScanFindingsForAddress also matches sweep recipients (whole-element LIKE with `:` suffix guard). Reports use the breakdown: the victim's tx tree/fund flows list every recipient with its own share; a recipient's own report links back to the victim and evidence names it "recipient" with its share. Tree nodes still show their own totals. Tests: TestScanFindingSweeps_Persistence, TestIngestScanFinding_SplitSweepRegistersRecipients, TestGetReport_TreeSplitSweep, TestGetReport_SplitSweepRecipientView.
- Stolen-funds movement tracking (watch): besides drainer-pattern txs, watch flags outgoing SOL transfers FROM known hacker wallets (hacker_movements in solana_scan.py; ≥TRACE_MIN_SOL, recipients that are exchanges/programs/off-curve are skipped — cashout, not accomplices). The hacker set is seeded from `GET /api/admin/wallets?status=hacker&chain=...` (admin key; handlers.ListAdminWallets → repository.ListWalletAddresses; comma-separated or repeated status params) plus `--hacker-file` (env SOLANA_HACKERS_FILE, default solana_hackers.json — optional, not shipped), and grows live: the operator of every DRAINER finding and every F2 recipient is watched immediately, so the chain unrolls recursively in real time. Recipients are classified like flow-trace: 1 transfer → SUSPICIOUS + F1_DOWNSTREAM_TRANSFER, 2+ transfers/sources → DRAINER + F2_REPEAT_DOWNSTREAM with empty victim (backend registers only the hacker side). Findings reuse F1/F2 indicators — no frontend/scanIndicatorMeta changes needed. Test: internal/handlers/admin_wallets_test.go (TestListAdminWallets).
- Fund-flow tracing (scan-wallet, on by default): after operators are identified, their outgoing SOL transfers are traced as distribution of stolen funds (`trace_fund_flows`, BFS over `load_wallet_txs` per wallet, flags `--trace-depth/--trace-wallets/--trace-txs/--no-trace`). Recipients classified by `classify_downstream`: 1 transfer = `suspicious`, 2+ transfers (or 2+ operator sources) = `hacker` (recursed into at next depth level), exchange wallets = `exchange` (terminal cash-out), programs/off-curve PDA = `program`. Report JSON gains `fund_flow` (level-0 edges victim→operator, then operator→downstream), `downstream_wallets`, `cashout_points`. API posting: suspicious → verdict SUSPICIOUS + indicator `F1_DOWNSTREAM_TRANSFER`; hacker → verdict DRAINER with EMPTY victim + `F2_REPEAT_DOWNSTREAM` (backend then registers only the hacker side); exchanges/programs are never posted. Source `flow-trace`. scanIndicatorMeta in handlers/scanner.go mirrors F1/F2.
- Exchange wallets: KNOWN_EXCHANGES (12 CEX hot/cold wallets: Binance, Coinbase, Bybit, OKX, Kraken, MEXC, Gate.io, HTX, Crypto.com — sourced from gelato.sh dataset) extended by `solana_exchanges.json` (`--exchanges-file` / env `SOLANA_EXCHANGES_FILE`); the file ships in build/dist via build.sh.

## Bulk check & live block scanners (liveblocksscan/)
- `POST /api/check/bulk` (public, handlers.BulkCheckWallets): `{chain, addresses[]}` → only addresses found in the threat DB **with a reported threat status — hacked/hacker/drained/phishing/suspicious (bulkCheckReportedStatuses); other registry rows are not disclosed**, with status/has_pk/has_seed/associated_hacker/reason/source, in request order. Cap 500 addresses; invalid/malformed inputs are skipped (checked/found counters). Accepts canonical chains and specific EVM networks (normalized via CanonicalChain); EVM matches case-insensitively (LOWER(address) IN ...). Repository: GetWalletsByAddresses. Tests: internal/handlers/bulk_check_test.go.
- EVM wallet identity: wallets table stores EVM addresses lowercase; repository.normalizeAddress (chain=evm → strings.ToLower) is applied on every read/write path (GetWallet, GetWalletByAddressAndChain, GetWalletReport, GetWalletStatus, GetWalletsByAddresses, CreateWallet, CreateWalletWithSeed, MarkAssociatedHacker, BatchAddWallets). No LOWER() in SQL and no generated column — plain indexed exact match on the existing (chain, address) index.
- liveblocksscan/ — stdlib-only Python live block watchers, one fully self-contained script per network. The 8 EVM chains (ethereum/bnb/base/linea/arbitrum/polygon/optimism/avalanche) share common.make_evm_watcher: native transfers from eth_getBlockByNumber (value>0 only — pure contract calls/approvals produce NO findings) + ERC20 Transfer logs from eth_getBlockReceipts (extract_erc20_transfers; token decimals/symbols come from KNOWN_TOKENS and, for unknown tokens, from on-chain eth_call decimals()/symbol() with an in-process cache — the finding then carries an `ERC20:<symbol>` meta-indicator, amount_sol is the correctly-scaled TOKEN amount; buildStatusEvidence skips `ERC20:` indicators, MonitorView uses them to show the token symbol; TRC20 transfers are labelled `ERC20:TRC20`; falls back to native-only with a one-time warning when the node lacks eth_getBlockReceipts). bitcoin.py — Esplora REST; solana.py — getSlot/getBlock system transfers ≥0.001 SOL; tron.py — TronGrid getnowblock, hex→base58check, TRC20 transfer decode (is_token); sui.py — checkpoints + balanceChanges (recipients only, abs amounts). common.py holds the shared core: JsonRpc rotation, ApiClient (bulk_check batches of 400, post_finding), run() loop from head forward. **Only real native/token transfers generate findings, and at most ONE finding per transaction** (process_transfers sorts transfers of a tx by amount desc, native before token, posts the first tracked one — other transfers of the same tx are skipped; counterparties are still registered via the findings). **Finding semantics**: outgoing from an OPERATOR address (hacker/suspicious only) → SUSPICIOUS + F1_DOWNSTREAM_TRANSFER, recipient registered as suspicious; incoming to any BAD_STATUSES threat address → SUSPICIOUS + L1_WATCHED_INFLOW, sender gets associated_hacker. Victim statuses (hacked/drained/phishing) never generate outgoing-side findings — after a drain they already lost the funds, their new outgoing activity is unrelated noise.
- Finding semantics (source `live-blocks`): outgoing FROM a threat-listed address → SUSPICIOUS + F1_DOWNSTREAM_TRANSFER, victim="", hacker=recipient, exposed=[sender] (tree/payout integration for free); incoming TO a threat-listed address → SUSPICIOUS + L1_WATCHED_INFLOW (meta in scanIndicatorMeta), victim=sender, hacker=known address in DB-form case, exposed=[sender]. Only BAD_STATUSES react — exactly hacked/hacker/drained/phishing/suspicious (vulnerable, scam, mixer, sanctioned, frozen, safe, exchange, unknown are ignored; the monitor feed is capped at 10). L1 ingest marks the funding sender associated_hacker — for L1 the victim field IS the funder, so the usual victim exclusion is skipped (TestIngestScanFinding_LiveInflowMarksAssociated).
